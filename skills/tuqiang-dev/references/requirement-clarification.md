# 需求澄清与用户决策门

本文件用于决定“现在可以实现，还是必须先问用户”。目标不是为每个技术细节索要批准，而是防止模型把产品、素材或契约缺口变成自己的设计。

## 1. 动手前写清两件事

开始修改前，用短句记录：

```text
用户可观察行为：<用户在什么条件下做什么，界面或系统应怎样表现>
可证伪验收标准：<什么输入/语言/平台/状态下，出现什么结果才算通过>
```

如果这两句无法唯一落地，先核对当前 Product Scope、需求上下文、调用链、现有 contract 和同产品同 owner 的 2–4 个成熟样本，不先写代码。

## 2. 必须由用户决定的缺口

以下信息缺失或存在多种合理解释，并且会改变结果时，立即停止写入并询问：

- 用户可见交互、条件分支、文案、排序、默认值或验收结果；
- PNG/SVG/动画、品牌色、业务图标、设计稿或多语言素材；
- API endpoint、字段、null/清空语义、错误码、权限或真实写操作授权；
- Android、iOS、HarmonyOS 的能力范围、降级方式、真机要求或供应商选择；
- 产品范围、阶段、阻塞项，尤其是老鹰在线 `docs/laoying/product_scope_matrix.md` 中未确认、阻塞、延期或永久排除的能力；
- 业务 owner、跨 package/public API、状态身份、路由 contract 或修改范围；
- 会扩大依赖、引入新外部包、改变现有行为或触碰用户未授权文件的方案。

不得用模型偏好、通用最佳实践、设计图里的额外元素、另一产品的实现或“先做一个看起来合理的版本”补全这些缺口。

## 3. 一次聚焦调查后的停止条件

一次聚焦调查只需要覆盖：

1. 目标产品与真实 owner；
2. 当前公开 contract、调用方和测试；
3. 同产品同 owner 的 2–4 个成熟样本；
4. 与需求直接相关的 Product Scope、API、路由、资源或平台约束。

完成后若仍有两种以上会改变用户可见行为或契约的合理实现，或者仍无法写出唯一可证伪验收标准，不继续扩大搜索、循环推理或试探性改代码。向用户提供：

```text
已确认：<源码/契约能证明的事实>
待决定：<一个明确问题>
方案差异：<各方案对行为、素材、范围或平台的影响>
建议：<有证据时给出推荐及理由；无足够证据时不强推>
```

等待用户决定后再实施相关部分。无依赖的只读调查可以继续，但不能用局部实现制造既成事实。

## 4. 可以自行决定的技术细节

当前产品、行为和验收已经明确，且同 owner 的调用方、测试和局部主流写法能唯一支持时，可以自行决定文件内命名、私有方法拆分、等价控制流和对应风险验证。若这些选择会改变 public API、owner、依赖方向、状态生命周期、产品表现或修改范围，则重新进入用户决策门。

## 5. 素材示例

现有地图起点/终点使用业务 PNG，需求要求非中文显示 `S/E`，但仓库没有对应素材时，正确动作是请求用户或设计提供目标 PNG，并确认语言切换规则。不得自行在“起/终”图片上叠字，也不得用 Canvas、系统图标或生成图片把“切换 asset”改成另一种视觉实现。完整边界见 [assets-guide.md](assets-guide.md)。
