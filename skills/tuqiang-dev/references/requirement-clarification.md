# 需求澄清

先从用户描述、已有授权、当前实现和直接调用方/测试确定验收与范围。内部命名、等价控制流和不改变行为的实现选择自行处理，不把普通工作升级成审批。

只有剩余未知会改变用户可见结果、外部契约或任务范围时才询问，例如：

- 账号/设备叶子选择会改变请求、缓存身份、UI 或 reset；
- API 的 null/清空含义、写操作或错误语义没有定义；
- 需求指定的业务素材缺失，或平台不支持时的产品行为未决定；
- 多种交互/默认值都有依据，现有需求与实现无法排除。

给出已确认事实、一个必要问题及方案的行为差异；只暂停依赖答案的改动，继续独立调查和可完成工作。不要因存在多个 route leaf 就必问：先检查用户是否已指定全部/局部，以及当前实现能否确定受影响范围。仅当叶子选择会改变实现且确实未定时询问。

不以默认个人模式、第一处搜索结果、自创接口、假素材或推测兼容填补影响验收的空白；不要反复确认用户已决定的选择。
