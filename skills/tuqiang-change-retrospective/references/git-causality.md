# Git 因果取证

用于回答“问题是哪次提交或改动造成的”。目标是证明行为因果，不是寻找某一行最后的作者。

## 1. 先定义四类角色

| 角色 | 定义 | 可能相同吗 |
|---|---|---|
| 缺陷引入改动 | 首次破坏业务不变量或遗漏必要保护 | 可以与暴露改动相同 |
| 问题暴露改动 | 让潜伏缺陷进入真实可达路径、扩大触发条件或让症状可见 | 可以晚于引入改动 |
| 修复改动 | 恢复业务不变量，阻断同一条错误传播链 | 可以尚未提交 |
| 防线缺失 | 本应发现或限制问题的测试、校验、日志、取消或生命周期清理缺口 | 通常不是单一提交 |

不要把最近提交、代码作者或报错首次出现时间自动写成根因。

## 2. 确定调查基线

按优先级选择范围：

1. 用户明确给出的 bad/good commit、PR 或提交区间；
2. 当前未暂存和已暂存修复 diff；
3. 当前对话中已经完成的文件和 symbol；
4. 与症状直接相关的近期提交。

先记录但不要改动仓库：

```text
git status --short
git branch --show-current
git rev-parse --short HEAD
git diff HEAD -- <path>
git diff -- <path>
git diff --cached -- <path>
```

`git diff HEAD` 用于看到暂存区与工作区相对 HEAD 的组合结果；另外两条用于区分修复分别位于 staged 还是 unstaged。

工作区有无关修改时，只调查目标 hunk。无法区分哪些改动属于本次复盘且这会改变归因时，再请求用户给文件、symbol 或提交范围。

## 3. 从修复反推错误版本

### 修复尚未提交

- 当前版本：工作区；
- 修复证据：优先查看 `git diff HEAD -- <path>`，再拆分 `git diff` 与 `git diff --cached`；
- 只有当 HEAD 中的目标代码可静态证明或由现有复现/测试证明包含同一缺陷，才能把 `HEAD` 当错误基线；
- 若 Bug 只存在于某个已经被覆盖的未提交中间态，最终工作区与 HEAD 无法证明该中间态的内容和先后顺序，必须标为“无法从 Git 确认”；
- 文档写“当前工作区修复，尚无修复提交”。

### 修复已经提交

- 修复版本：`<fix-sha>`；
- 错误基线：通常是 `<fix-sha>^`，合并提交则先确认正确父提交；
- 用 `git show <fix-sha> -- <path>` 确认真正恢复了什么不变量；
- 用 `git show <fix-sha>^:<path>` 查看修复前代码。

不要在当前已修复的行上直接 blame；优先对“修复前版本中的错误行”调查。

## 4. 只读搜索序列

根据实际 symbol 和文件裁剪命令：

```text
git log --follow --date=short --format="<format>" -- <path>
git log -S "<exact-text>" --date=short -- <path>
git log -G "<regex>" --date=short -- <path>
git blame -w -M -C <pre-fix-rev> -L <start>,<end> -- <path>
git show --stat <candidate-sha>
git show <candidate-sha> -- <path>
git show <candidate-sha>^:<path>
```

- `--follow` 只适合单文件重命名历史；
- `-S` 查某段文本数量发生变化，适合字段、条件或调用首次出现；
- `-G` 查 diff 中匹配正则的行，适合语法变化；
- `blame -w -M -C` 只提供移动/复制后的来源线索；
- 必须阅读候选提交及其父版本的上下文，不能只看 subject。

本 Skill 永不运行 `git bisect`：它会切换工作树并可能触发构建或测试副作用。若精确归因必须依赖二分，文档说明需要的 good/bad 范围与自动化判定条件，并建议用户另开隔离任务后单独授权。

## 5. 因果确认问题

对每个候选改动逐项回答：

1. 父版本是否仍满足业务不变量？
2. 候选改动具体破坏了哪个条件、身份、时序、清理或边界？
3. 这条错误是否能沿真实入口、数据和状态链到达用户症状？
4. 是否只是移动/格式化代码，实际错误更早已存在？
5. 后续是否有另一改动才让它变得可达或可见？
6. 修复是否恢复同一个不变量，而不是仅隐藏 UI 症状？
7. 结论是否得到测试、复现步骤、日志或用户确认支持？

## 6. 置信度

对“缺陷引入”“问题暴露”“修复”分别定级，不能用一个总置信度替代各角色证据：

| 等级 | 历史引入/暴露角色 | 修复角色 |
|---|---|---|
| 已确认 | 候选提交与父版本差异、真实传播链，以及历史版本复现或修复前失败测试形成闭环 | 修复前失败、修复后通过的测试/复现，或当前用户确认能直接证明同一症状恢复 |
| 高度可能 | 提交差异、传播链与修复闭环清晰，但未在历史版本运行复现 | 修复 diff 明确恢复同一不变量，但只完成静态核验 |
| 候选 | 主要来自 blame、`-S/-G` 或提交信息，尚未证明行为可达 | 只有表面相关改动，未证明症状或不变量恢复 |
| 无法确定 | 浅克隆、历史重写、缺少父版本或范围无法分离 | 无法分离目标修复，或中间态已经丢失 |

用户确认“现在修好了”只支持修复角色，不自动确认历史引入/暴露提交。修复尚未提交只表示没有修复 SHA，不会自动降低历史引入角色的置信度。

“高度可能”不写成“就是”。多个提交共同造成时分别列出角色，不强行选一个罪魁祸首。

## 7. 归因表

最终文档至少包含：

| 角色 | commit/工作区 | 改动事实 | 因果说明 | 证据 | 置信度 |
|---|---|---|---|---|---|
| 缺陷引入 |  |  |  |  |  |
| 问题暴露 |  |  |  |  |  |
| 修复 |  |  |  |  |  |
| 防线缺失 | 不一定对应提交 |  |  |  |  |

提交只展示 short SHA、日期和 subject；作者不是学习因果所必需，默认不突出个人。

## 8. 特殊情况

- **当前改动曾引入又修复**：最终 diff 不能证明已经消失的未提交中间态及其先后顺序；只有聊天记录、补丁快照或其他可核验证据存在时才写该过程，否则标为未知，不造 SHA。
- **squash/rebase 后历史被压平**：只能归因到可见提交，说明原始细粒度历史不可恢复。
- **代码生成或批量迁移**：区分生成器/迁移规则与生成文件；根因可能在规则而不是最后生成行。
- **后端/SDK 行为改变**：若仓库只能证明输入输出边界，不推断外部发布日期或实现原因。
- **测试后来才新增**：测试提交通常属于防线补强，不自动等于缺陷引入提交。
