# 复盘内容与输出约定

生成一份脱离聊天也能读懂的 Markdown。写复盘文档不代表获得修改业务代码、测试、配置或 Git 的权限。

## 文件

- 路径优先级：用户指定文件 → 用户指定目录 → 项目规范 → `docs/learning`。默认名 `YYYY-MM-DD-{bug|feature|hybrid}-<safe-kebab-slug>.md`。
- 不覆盖已有文件（用户明确要求更新原文除外），重名加 `-2`、`-3`。UTF-8 无 BOM，末尾换行。

## Bug

说明用户看到什么、正确行为是什么、哪条约束被破坏、修复如何恢复它；期望来自推测时标明。从触发条件找到错误发生点与最终消费者：简单默认值或条件修复用一段前后对照；跨文件、异步或响应式问题再区分事件、数据完成与状态/UI 更新。说明修复阻断了哪一步，以及测试、复现或用户确认分别证明了什么。预防措施直接对应根因（现有边界中的一处约束或能复现症状的回归用例），不凑评审问题与检查矩阵。

## 需求

从"用户目标 → 可验收行为 → 关键实现 → 证据"展开，不按文件清单堆叙述；产品动机只有用户、工单或明确说明支持时才写为事实。聚焦：完成了哪个行为、验收来自哪里、哪些未验证；用了哪个现有 owner/状态/函数/组件及原因；数据流决定行为时追输入、关键转换与最终消费者。取舍用当前契约与调用方证据支持，"为了可维护性"本身不是证据；Git 无法证明开发顺序时标注"按最终 diff 解释"。

## 混合改动

以需求为主线，在相关实现处说明 Bug 是新引入、暴露旧问题还是独立修复；证据不足保留未知。仍只输出一份文档。

## 内容裁剪

每份文档说明对象/范围、结果、关键原因或实现、证据与实际验证状态，可写成短段落。分支/HEAD、未提交状态、账号/平台只记录足以辨认本次改动的信息。无关栏目直接省略，不写"不适用"；不强制因果金字塔、泳道、全量矩阵或证据账本。

## 证据与完成检查

- 当前代码用仓库相对路径与实时 1-based 行号；历史代码用 `path@short-sha`，不伪造旧行号。摘录只保留证明关键变化所需的源码。
- 已证实事实、推断与未知分开；Git 归因按 [Git 因果](git-causality.md) 标注角色与置信度。
- 用户确认、静态检查、测试、真机或集成结果分别说明；未执行的验证不写成通过（项目默认禁止执行 `flutter test`，测试未运行如实写明）。
- 后端、SDK 或不可见历史写清证据停止点；不输出 endpoint、Token、Key、AK、证书或生产配置。
- 检查未覆盖旧文件，链接、行号与 SHA 可核验。
