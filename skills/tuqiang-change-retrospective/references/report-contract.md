# Markdown 输出契约

每次调用必须生成一份可独立阅读的 Markdown 文件。用户不需要回看聊天记录才能理解文档。

## 1. 路径与文件名

优先级：

1. 用户指定文件；
2. 用户指定目录；
3. 目标仓库文档规范；
4. `<TUQIANG_ROOT>/docs/learning/`。

文件名：

```text
YYYY-MM-DD-bug-<slug>.md
YYYY-MM-DD-feature-<slug>.md
YYYY-MM-DD-hybrid-<slug>.md
```

- slug 使用简短、可识别、跨平台安全的 kebab-case；无法自然转成英文时可用简短中文，但移除 `<>:"/\|?*`；
- 不覆盖已有文件；依次尝试 `-2`、`-3`、……直到首个不存在的名称，并在写入前再次检查；
- 只有用户明确要求更新某份现有复盘时才原地编辑；
- 使用 UTF-8 无 BOM，文件末尾保留换行。

## 2. 文档元信息

标题后立即给出：

| 字段 | 内容 |
|---|---|
| 复盘模式 | Bug / 需求 / 混合 |
| 产品线 | Tuqiang / Laoying / 共享 / 双产品 |
| target / 平台 | `standard`、`ohos`、`laoying_standard`、`laoying_ohos` 中实际受影响项；未知时写未知 |
| 复盘范围 | 用户给出的提交区间、工作区 diff、文件或 symbol |
| 仓库基线 | 分支、short HEAD、工作区是否有目标相关未提交改动 |
| 生成日期 | 本地日期 |
| 验证状态 | 用户确认、测试、analyze、真机/集成分别列出 |
| 归因置信度摘要 | 缺陷引入、问题暴露、修复分别写“已确认 / 高度可能 / 候选 / 无法确定”；不适用的角色写“不适用” |

不输出含凭据的 remote URL。分支为空时写 detached HEAD，不猜分支名。产品线、target、范围或产品意图存在多解且会改变结论时，生成文件前先询问；不改变结论时写入“未知边界”，不要静默选择或从源码反推产品意图。

## 3. 通用开头

所有模式都先写：

1. **30 秒结论**：初学者能在一段话内知道发生了什么、为什么和最终怎样；
2. **范围与边界**：纳入哪些文件/提交，哪些外部系统或验证不可见；
3. **金字塔总览**：纯文本图，从用户价值/症状下钻到源码和证据；
4. **术语提示**：只解释本文真正出现且初学者可能陌生的 3–8 个术语。

## 4. Bug 文档结构

```markdown
# Bug 复盘：<标题>

## 30 秒结论
## 复盘范围与验证状态
## 现象、触发条件、期望与实际
## 因果金字塔与因果栈
## 缺陷引入、问题暴露、修复与防线时间线
## 同步事件链
## 异步数据链
## 状态依赖与 UI 重建链
## 输入输出在哪一步偏离
## 修复前与修复后的真实源码/资源证据
## 前端对照（适用或用户要求时：Vue3 / React）
## 为什么修复有效
## 本次实际排查过程
## 下次如何快速排查
## 如何避免：代码、测试、评审与日志
## 证据账本与置信度
## 未知边界
## 学习总结与复习问题
```

没有证据的章节不要编造。用户明确要求的核心问题若无法确认，用一两句话写明所缺证据；其余未知集中到“未知边界”，不要在多个章节重复。

## 5. 需求文档结构

```markdown
# 需求复盘：<标题>

## 30 秒业务结果
## 复盘范围与验证状态
## 背景、目标与验收标准
## 为什么这样设计
## 需求实现金字塔
## 涉及模块与 owner
## 用户入口与同步事件流
## 异步数据流
## 状态写入、消费与 UI 重建
## 输入输出血缘表
## 关键真实源码/资源证据
## 前端对照（适用或用户要求时：Vue3 / React）
## loading、error、empty、并发与生命周期
## 实现过程与关键取舍
## 测试和验证
## 已证实事实、推断与未知边界
## 学习总结与复习问题
```

## 6. 混合文档结构

以需求结构为主，在受影响步骤后增加：

```markdown
## 开发过程中涉及的 Bug
### Bug 卡 1：<标题>
#### 与需求主线的关系
#### 引入 / 暴露 / 修复证据
#### 因果栈与修复过程
#### 排查、避免和回归验证
```

复杂 Bug 可采用完整 Bug 结构，但默认仍只输出一个文件。

## 7. 图、表与时间流

- 至少一份纯文本金字塔或因果栈，不能只依赖 Mermaid；
- Mermaid 仅在能提高可读性且渲染环境可能支持时附加；
- 同步事件、异步数据、状态/UI 使用三条独立泳道；
- 输入输出使用固定血缘表；
- Git 使用“角色—改动—因果—证据—置信度”表。

## 8. 源码证据

- 文档内使用仓库相对路径，例如 `packages/feature/.../foo.dart:42`；
- 当前行号必须从当前 checkout 实时获取；
- 历史片段写 `packages/.../foo.dart@abc1234`，避免伪造旧行号；
- 每段代码前说明它证明什么，代码后解释输入、输出和下一跳；
- 单段只保留理解该跳所需内容，禁止复制整文件；
- 修复前、修复后、Vue3、React 使用相同的业务步骤编号；
- 对 endpoint、Token、证书、签名和生产配置脱敏或完全省略。

原生插件、资源、i18n manifest 或构建改动还要按实际类型取证：Dart 调用、Java/Swift/ETS 加载、`pubspec.yaml`/manifest 注册、资源路径与必要的尺寸/hash/测试。二进制 diff 只能证明文件发生变化；没有需求、验收或视觉确认时，不能从图片像素或 commit subject 推导产品意图。Vue3/React 仅在能解释同一业务状态链或用户明确要求时加入，不为满足模板替代真实平台证据。

## 9. 初学者友好，但不牺牲准确性

- 先用白话给结论，再给 Flutter/Riverpod 正式术语；
- 区分路由参数、family key、action 参数和 State 字段；
- 明确 `await` 之后不是原同步栈继续“同时运行”；
- 明确 Provider 通知/Widget 重建是响应式依赖，不是普通函数逐层回调；
- 每个“为什么”尽量指向代码、提交、测试或明确需求；
- 复习问题限制在 3–5 个，答案应能从文档中找到。

## 10. 篇幅与去重

“完整”是指入口、数据、状态、UI、Git/实现依据和验证边界形成闭环，不是把模板每一项都扩写成长文。

- 同一事实、因果和源码片段只在一个主章节完整解释，其他位置引用步骤编号、表格行或小节；
- 金字塔讲“为什么和层级”，三泳道讲“什么时候”，源码讲“证据”，三者不要逐句重复；
- 输入输出表已经说明的简单搬运步骤，正文只展开会改变语义、状态身份或时序的节点；
- 需要 Web 对照时 Dart、Vue3、React 保持端到端同链，并共享步骤编号和数据契约；不要在三套代码后重复三遍同一业务说明；
- 不适用的模板章节可以合并或用一句话说明，不为满足标题清单填充空泛内容；
- 复杂链路可把详细 Git 命令、完整证据表或次要分支放在文末附录，让前半部分仍适合初学者顺序阅读。

## 11. 输出前自检

- [ ] 文档无需聊天上下文即可独立理解；
- [ ] 路径、symbol、当前行号和 SHA 可核验；
- [ ] 事实、推断、未知和验证状态没有混淆；
- [ ] Git blame 未被当作单独归因证据；
- [ ] 产品线与实际受影响 target 已记录；会改变结论的多解已先询问；
- [ ] 需要前端对照时 Dart、Vue3、React 链路字段一致；否则真实平台/资源证据已覆盖改动；
- [ ] 同步、异步与响应式更新没有画成伪调用栈；
- [ ] 同一结论和源码没有跨章节重复展开，完整性来自证据闭环而非堆叠篇幅；
- [ ] 没有敏感信息、机器专属绝对路径或整文件源码；
- [ ] 文件未覆盖旧文档，编码为 UTF-8 无 BOM；
- [ ] 最终回复提供绝对文件链接。
